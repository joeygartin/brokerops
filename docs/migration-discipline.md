# Migration discipline (upgrade + rollback rules)

The fleet upgrade driver (`scripts/fleet_upgrade.py`, BOP-033) rolls each client instance
forward to a pinned release. Database schema is the one part of an upgrade that is **not**
freely reversible — a Cloud Run revision rolls back in seconds, a dropped column does not.
These rules keep "roll it back" a real option.

## The container runs migrations on start

Each api container runs `alembic upgrade head` against the client's database as it boots
(the deploy path, ADR-0025). Two consequences the release process is built around:

- **A new tag's migrations apply the moment its revision goes live** — there is no separate
  "migrate" step to forget or to gate on. The upgrade *is* the migration.
- **Redeploying an older tag does NOT undo a migration.** The old image simply starts
  against the already-migrated schema. So rollback safety is decided entirely by *what the
  migration did*, not by which image is running.

## Forward-only Alembic

Migrations are **forward-only**. We do not rely on `downgrade()` to reverse a production
schema (an autogenerated `downgrade` is often lossy or wrong, and nothing runs it on a tag
rollback anyway). To change or remove schema, write a *new* forward migration.

- Every migration has a real `upgrade()`; `downgrade()` may raise `NotImplementedError`
  rather than pretend.
- Migrations are **additive by default** — add tables/columns/indexes; backfill in the same
  or a follow-on migration; only *later*, once no running revision reads the old shape,
  remove it (the expand → migrate → contract pattern).

## Destructive migration — the definition that gates rollback

A migration is **destructive** if a straight redeploy of the previous tag could not run
correctly against the schema it leaves behind. Concretely, it:

- drops a table, column, or index that a shipped revision still reads or writes;
- renames a table or column (a drop + add from the old image's point of view);
- narrows a type, adds a `NOT NULL` without a default, or adds a constraint the old
  image's writes would violate;
- rewrites or deletes data the old image depends on.

Additive migrations (new nullable column, new table, new index, new enum value) are **not**
destructive: the previous image ignores what it does not know about, so its revision still
runs.

## Rollback rule

> **Rollback = redeploy the previous tag — allowed *only if no destructive migration has
> shipped since that tag.***

- **No destructive migration since?** Roll back by redeploying the old tag
  (`make deploy CLIENT=<c> VERSION=<old>` or a targeted `fleet_upgrade.py <old> --client <c>`).
  The newer additive schema stays; the old code ignores it.
- **A destructive migration shipped since?** A tag rollback is **not** safe — the old image
  would hit schema it cannot run against. Recover forward instead: write a new migration
  that restores the needed shape, or restore from the pre-upgrade dump (below). Never
  "just redeploy the old tag" across a destructive boundary.

## Pre-upgrade `pg_dump` (per client, every upgrade)

Before applying an upgrade to a client, take a dump of **that client's** database so a
destructive migration or a bad backfill has a floor to restore to:

```bash
# The client's DATABASE_URL / Cloud SQL instance — never a shared one.
pg_dump "$CLIENT_DATABASE_URL" --format=custom --file="backup-<client>-<old-version>.dump"
```

Keep it until the new release has been healthy in production long enough to trust
(a release cycle). Restore, if ever needed, with `pg_restore` into a fresh database and
repoint the client, rather than restoring in place over live data.

## Release checklist (the gate)

Before cutting a release tag that the fleet driver will roll out, confirm:

- [ ] Every new migration has a working `upgrade()`; none is relied on to `downgrade()`.
- [ ] Each migration is classified **additive** or **destructive** (definition above).
- [ ] If any migration is **destructive**, the release notes say so explicitly, and the
      rollout plan does not assume a tag rollback is available across it (expand →
      contract split across two releases is preferred to a single destructive one).
- [ ] A per-client `pg_dump` is taken immediately before each client's upgrade.
- [ ] The driver's post-apply verify (`/readyz` 200 + the authenticated smoke) is green
      for each client before the walk continues.

The fleet driver enforces the last point mechanically (it stops the walk on the first
verify failure); the rest are human discipline this doc exists to make routine.
